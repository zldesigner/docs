# 交互范式

## Agent 产品的交互特征

运动健康 Agent 的交互与传统 App 有本质区别：

| 维度 | 传统 App | Agent 产品 |
|-----|---------|-----------|
| 主要界面 | 视觉界面（按钮、表单、列表） | 对话界面（自然语言） |
| 交互发起方 | 用户主动操作 | 用户或 Agent 均可发起 |
| 信息组织 | 层级导航 | 上下文感知 |
| 个性化方式 | 设置页面 | 对话中动态适应 |
| 错误处理 | 弹窗 + 提示 | 对话式澄清和恢复 |

## 核心交互模式

### 模式一：请求-响应模式

最基本的交互模式，用户提问或请求，Agent 响应。

```
适用场景：
- 用户有明确的信息需求
- 用户请求执行特定任务

设计要点：
- 响应要即时（感知延迟 < 1 秒开始显示）
- 使用流式输出（打字效果），不要等全部生成再展示
- 长回复用分段展示，不要一次输出巨量文字
```

**响应时间规范：**

| 操作类型 | 可接受延迟 | 超时处理 |
|---------|-----------|---------|
| 简单问答 | < 2秒 | 3秒后显示"正在思考..." |
| 计划生成 | < 5秒 | 2秒后显示进度提示 |
| 数据分析 | < 8秒 | 2秒后显示"正在分析你的数据..." |
| 复杂多Skill | < 10秒 | 分步骤展示进度 |

### 模式二：主动介入模式

Agent 主动发起对话，而不是等待用户。这是 Agent 区别于传统 App 的核心能力之一。

<AccordionGroup>
  <Accordion title="适当的主动介入场景">
    ✅ **应该主动介入的场景：**
    - 检测到用户连续多天未完成计划
    - 发现数据异常（睡眠持续不佳、体重趋势反转）
    - 里程碑完成时的即时庆祝
    - 周期性复盘（每周/每月）
    - 基于日历的训练提醒（如果用户开启）

    ❌ **不应该主动介入的场景：**
    - 用户设定了"请勿打扰"时段
    - 同一天已经发起过主动对话
    - 用户昨天表示"不需要这么多提醒"
    - 没有实质性内容的"刷存在感"推送
  </Accordion>
  <Accordion title="主动介入的措辞设计">
    主动介入消息应该：
    1. 开门见山，直接说明原因（不要"嗨！我有话说"这样的过渡）
    2. 内容有价值（基于真实数据或真实情况）
    3. 提供明确的行动选项（不只是说完就结束）

    ```
    ✅ 好的主动介入：
    "你已经有4天没有训练了，是遇到什么情况吗？
     如果需要，我可以帮你重新调整本周的计划。"
    
    ❌ 差的主动介入：
    "嗨！好久没见你训练了！记得要保持运动哦！💪"
    ```
  </Accordion>
</AccordionGroup>

### 模式三：引导式对话模式

当用户需要做出复杂决策或完成结构化任务时，Agent 主导对话流程。

```
应用场景：
- 首次目标设定
- 初始训练评估
- 周期复盘
- 运动计划定制

设计要点：
- 让用户感知到对话在推进（"第2步，共4步"）
- 允许随时跳出（"可以先保存这里，下次继续"）
- 允许回退（"我想修改之前的答案"）
- 在关键节点汇总确认，而不是到最后才发现错误
```

**引导式对话的进度指示：**
```
[目标设定向导] 第 2 步 / 共 4 步

✅ 基本信息  →  📍 健康目标  →  ○ 时间安排  →  ○ 生成计划

你的主要健康目标是什么？
...
```

### 模式四：卡片+对话混合模式

对于结构化信息（训练计划、营养分析、周报），用卡片承载，对话提供解读和交互。

```
卡片呈现：结构化数据、计划详情、报告摘要
对话提供：解读、追问、调整请求

示例界面结构：

┌────────────────────────┐
│   今日训练计划          │  ← 卡片区域
│   腿部力量训练          │
│   ⏱ 45分钟  🔥 中等强度│
│                         │
│   [开始训练]  [调整计划]│
└────────────────────────┘

Agent：今天是腿部训练日！🏋️
       主要包含深蹲、腿举和腿弯举，
       这组动作对你的减脂目标特别有效。
       
       你昨晚睡了8小时，今天状态应该不错。
       准备好了吗？有什么需要调整的吗？
```

## 多模态交互设计

### 语音交互

运动场景天然适合语音交互（双手被占用时）：

```
运动中的语音交互场景：
- 跑步时查询配速建议
- 力量训练时记录完成组数
- 运动后口述今日感受

语音交互设计原则：
1. 指令要简短：支持"记录完成"、"下一组"、"调整重量"等短指令
2. 反馈要简洁：语音回复不超过15秒
3. 确认要清晰："已记录，继续加油"而不是长篇解释
4. 降噪能力：考虑健身房噪音环境的识别准确率
```

### 表单与快速选择

某些场景下，结构化表单比纯对话更高效：

```
适合用表单/快速选择的场景：
- 身体基本信息输入（一次性，信息密集）
- 食物快速记录（高频，需要速度）
- 偏好设置（多维度，对话会很繁琐）

设计原则：
- 表单内嵌于对话流中，而不是跳转到独立页面
- 完成后继续回到对话模式
- 提供对话模式作为备选（"更喜欢告诉我？"）
```

## 通知设计规范

### 通知类型与优先级

```
P0 - 即时通知（立即推送）：
  - 里程碑完成庆祝
  - 运动异常预警（心率异常等）
  - 时间敏感的训练提醒（训练开始前15分钟）

P1 - 汇总通知（合并推送，避免打扰）：
  - 日常数据更新
  - 饮食记录提醒（按固定时间合并）
  - 一般性洞察和建议

P2 - 周期通知（固定时间，用户可配置）：
  - 周报、月报
  - 目标进度更新
  - 定期复盘提醒
```

### 通知文案规范

```
通知标题：< 15字，直接说明内容
通知正文：< 40字，一句话，包含核心价值

✅ 好的通知：
标题：你完成了第100次训练！
正文：三个月前你还说"我坚持不下去"，今天你做到了。

❌ 差的通知：
标题：健康提醒
正文：您好，请记得今天完成您的训练计划，保持健康生活方式。
```

## 错误状态设计

### 数据同步失败

```
Agent：我刚才无法读取你的手表数据，可能是蓝牙连接问题。

       这几种方式可以解决：
       ① 在手机蓝牙设置中重新连接手表
       ② 手动告诉我今天的运动情况
       ③ 稍后再试（数据会自动补同步）

       你今天运动了吗？
```

### Skill 执行失败

```
当 Skill 无法正常执行时：
- 不暴露技术错误信息
- 提供替代方案
- 保存用户的上下文，确保恢复时不需要重新开始
- 如果是系统问题，主动告知预计恢复时间
```

## 无障碍设计规范

- **字体大小**：支持系统字体缩放，最小正文不小于16sp
- **颜色对比**：对话气泡颜色对比度 ≥ 4.5:1
- **语音支持**：所有核心功能支持语音输入和TTS输出
- **图表替代文本**：所有数据图表配备数据表格备选视图
